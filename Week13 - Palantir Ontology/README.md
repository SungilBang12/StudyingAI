# Week13 - Palantir Ontology

> [!abstract] 이번 주의 설계 질문
> 현실의 객체·관계·행동을 표현해 실제 업무 규칙과 연결하는 법을 익힌다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 원천 데이터 → 객체·속성·링크 → 규칙·권한 → Action → 상태 변화·감사 기록

## 1. 핵심 원리 이해

- [ ] 테이블 행, 현실 객체, 객체에 허용된 행동이 각각 무엇인지 구분한다.
- [ ] 관계를 보여주는 그래프와 상태 변경 규칙을 포함한 운영 온톨로지의 차이를 설명한다.

## 2. 시스템 아키텍처 관찰

- [ ] Task·Project·Person 객체와 소유·의존 관계를 그린다.
- [ ] ‘작업 완료’ Action의 입력, 사전 조건, 결과 상태, 실행 이력을 따라간다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 객체 경계, 식별자, 관계의 cardinality, 필수 속성, Action 사전 조건을 후보로 정한다.
- [ ] 데이터 최신성 규칙과 역할별 행동 권한이 사용 경험에 미치는 영향을 관찰한다.

## 4. Baseline 구현

- [ ] 실제 플랫폼 접근이 없어도 JSON 또는 SQLite로 세 객체 유형과 관계를 표현한다.
- [ ] 완료 조건을 검사하는 함수 하나를 만들고, Palantir 자체 구현이 아닌 개념 모형임을 명시한다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 같은 사례에서 ‘상태를 자유 문자열로 저장’과 ‘허용 상태로 제한’ 조건 하나만 바꾼다.
- [ ] 별도 실험으로 의존 작업 완료를 사전 조건에 추가하고 처리 가능한 작업 수와 오류를 비교한다.

## 6. 성능 측정 지표

- [ ] 규칙 위반 상태 수, 필수 관계 누락 수, 올바른 Action 성공률을 기록한다.
- [ ] 원천 데이터부터 결과 상태까지 추적 가능한 변경 비율과 새 규칙을 추가하는 데 든 시간을 기록한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 중복 ID, 존재하지 않는 담당자, 순환 의존 관계를 넣는다.
- [ ] 허용되지 않은 역할의 Action과 같은 Action의 재실행을 모의 환경에서 검사한다.

## 8. 내 방식으로 재설계

- [ ] 내 업무에서 자주 묻는 질문 하나를 정하고 그 질문에 필요한 객체·관계만 남긴다.
- [ ] 규칙을 여러 화면에 흩뜨리지 않고 Action 경계에서 한 번 검사하도록 바꾼다.

## 9. 최종 회고

- [ ] 현실을 더 잘 표현한 구분과 유지 비용만 늘린 구분을 각각 적는다.
- [ ] 내가 정의한 세계가 무엇을 표현하지 못하는지와 확장할 조건을 정리한다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
