# Week08 - LangGraph & Agents SDK

> [!abstract] 이번 주의 설계 질문
> 에이전트의 상태·도구·종료 조건을 명시적으로 다뤄 중단과 재개를 설계한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 입력 → 상태 → 노드 또는 에이전트 → 도구 → 결과 갱신 → 분기·종료

## 1. 핵심 원리 이해

- [ ] 명시적인 상태 그래프와 에이전트에게 도구 선택을 맡기는 구조의 차이를 설명한다.
- [ ] handoff, 일반 함수 호출, 상태 전이가 언제 같은 의미가 아닌지 예를 든다.

## 2. 시스템 아키텍처 관찰

- [ ] LangGraph와 Agents SDK를 별도로 관찰하고, 상태 저장·추적·재개 방식이 동일하다고 가정하지 않는다.
- [ ] 사용 버전 문서에서 실제 제공 기능을 확인하고, 반복 중 상태와 외부 부작용이 저장되는 지점을 그린다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 자체 흐름의 최대 단계 수, 재시도 수, 도구 timeout, 상태에 남길 필드를 정한다.
- [ ] 체크포인트나 사람 검토 단계는 사용 도구가 지원하는 방식으로 배치한다.

## 4. Baseline 구현

- [ ] 둘 중 하나를 골라 ‘분류 → 가짜 조회 도구 → 결과 검증’의 세 단계 흐름을 구현한다.
- [ ] 요청 ID·단계·도구 결과·오류 상태를 기록하고 정상 종료와 실패 종료를 각각 실행한다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 동일한 입력·모의 실패 순서에서 재시도 수만 0/1/2로 바꾼다.
- [ ] 시간이 남으면 다른 프레임워크로 같은 계약을 표현하되 프레임워크 비교는 별도 실험으로 기록한다.

## 6. 성능 측정 지표

- [ ] 작업 성공률, 평균 단계 수, 복구 성공률을 기록한다.
- [ ] 같은 요청의 중복 부작용 수와 재시작 후 잃어버린 상태 수를 센다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 도구 timeout과 중간 프로세스 중단을 주입해 무한 루프·중복 실행 여부를 확인한다.
- [ ] 결제 대신 카운터를 증가시키는 모의 도구로 재시도가 부작용을 두 번 만드는지 시험한다.

## 8. 내 방식으로 재설계

- [ ] 모든 단계를 에이전트에게 맡기지 않고 결정적인 검증은 일반 함수로 옮긴다.
- [ ] 요청 ID로 중복 부작용을 막거나 명시적 종료 조건을 추가해 동일 실패 시나리오를 재실행한다.

## 9. 최종 회고

- [ ] 상태를 명시해서 해결된 문제와 불필요하게 복잡해진 부분을 적는다.
- [ ] 다음 작업에 그래프가 필요한지 단순 함수 흐름이면 충분한지 근거를 남긴다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
