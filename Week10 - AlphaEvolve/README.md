# Week10 - AlphaEvolve

> [!abstract] 이번 주의 설계 질문
> 자동 평가기를 통해 생성된 코드가 어떤 방향으로 진화하는지 조정한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 초기 코드 → 후보 생성 → 정확성 검사 → 성능 평가 → 후보 보관·선택 → 다음 세대

## 1. 핵심 원리 이해

- [ ] 코드를 잘 생성하는 것과 좋은 후보를 정확히 선별하는 것의 차이를 설명한다.
- [ ] 평가 가능한 목표가 진화 방향을 결정하며, 평가기의 허점을 개선으로 착각할 수 있음을 이해한다.

## 2. 시스템 아키텍처 관찰

- [ ] 후보 코드·부모 후보·수정 이유·검증 결과·점수의 계보를 남긴다.
- [ ] 정확성 검사를 통과한 후보만 성능 순위에 넣는 순서를 그린다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 후보 수, 세대 수, 선택할 상위 후보 수, 다양성 유지 기준을 정한다.
- [ ] 속도·메모리 목표를 정하되 정확성은 타협 가능한 가중치가 아니라 통과 조건으로 둔다.

## 4. Baseline 구현

- [ ] 작은 순수 함수와 신뢰할 수 있는 정답 구현, 고정 입력 세트를 준비한다.
- [ ] 제한된 실행 환경에서 후보 생성 → 정답 대조 → 시간 측정 → 최선 보관의 학습용 루프를 만든다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 동일한 평가 예산에서 보관 후보 수만 1/3/5로 바꾼다.
- [ ] 튜닝에 쓰지 않은 입력 크기와 경계값으로 개선이 일반화되는지 확인한다.

## 6. 성능 측정 지표

- [ ] 정확성 통과율, baseline 대비 실행 시간 비율, 최대 메모리 사용량을 기록한다.
- [ ] 워밍업 후 반복 측정의 중앙값·변동 폭과 유효 후보 한 개를 얻는 비용을 기록한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 빈 입력·큰 입력·중복값·평가 시간 초과를 넣어 빠르지만 틀린 후보를 탈락시킨다.
- [ ] 특정 공개 테스트 결과만 하드코딩한 모의 후보를 숨긴 테스트가 잡아내는지 확인한다.

## 8. 내 방식으로 재설계

- [ ] 평균 속도만 최적화하는 대신 내가 중요하게 보는 최악 입력 지연이나 메모리 한도를 반영한다.
- [ ] 바뀐 평가 기준으로 짧게 다시 실행해 선택되는 코드의 성질이 달라지는지 본다.

## 9. 최종 회고

- [ ] 가장 큰 개선이 생성 능력에서 왔는지 평가 설계에서 왔는지 기록한다.
- [ ] 점수는 좋아졌지만 원치 않았던 코드와, 내 기준에서 남길 후보를 설명한다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
