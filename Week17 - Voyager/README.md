# Week17 - Voyager

> [!abstract] 이번 주의 설계 질문
> 경험을 재사용 가능한 기술로 저장하면 새로운 과제를 더 잘 푸는지 검증한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 환경 상태 → 자동 과제 제안 → 코드 행동 → 실행 피드백 → 수정 → skill 저장·검색

## 1. 핵심 원리 이해

- [ ] 자동 curriculum, 실행 피드백 기반 수정, skill library의 역할을 설명한다.
- [ ] 기술 재사용과 모델 가중치 학습을 구분하고, 코드 저장만으로도 배울 수 있는 것을 적는다.

## 2. 시스템 아키텍처 관찰

- [ ] 관찰 상태가 과제 선택과 코드 생성에 어떻게 들어가는지 추적한다.
- [ ] 기술의 설명·입력·사전 조건·성공 여부가 저장과 검색에 필요한 이유를 관찰한다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 과제 난이도 증가 폭, 수정 시도 수, 기술 검색 top-k, 저장 성공 기준을 후보로 둔다.
- [ ] 환경 reset 정책과 이미 수행한 기술의 재검증 시점을 정한다.

## 4. Baseline 구현

- [ ] Minecraft 설치가 부담되면 열쇠·문·도구가 있는 작은 텍스트 또는 격자 환경을 만든다.
- [ ] 코드 행동 3~5개와 성공 검사를 구현하고 skill library 없는 버전을 대조군으로 둔다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 동일한 과제 순서에서 skill library 사용 여부만 바꾼다.
- [ ] 별도 실험에서 재시도 횟수만 바꿔 실패를 고치는 능력과 비용을 비교한다.

## 6. 성능 측정 지표

- [ ] 새 과제 성공률, 성공까지 환경 step 수, 기술 재사용률을 기록한다.
- [ ] 저장된 기술의 재실행 성공률과 과제당 코드 수정 횟수를 측정한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 문 위치나 도구 이름을 바꾸고 기존 기술이 잘못된 전제에 의존하는지 본다.
- [ ] 일부만 성공한 기술과 실행 오류를 주입해 실패한 기술을 성공으로 저장하는지 확인한다.

## 8. 내 방식으로 재설계

- [ ] 기술에 사전 조건·사후 조건을 붙여 적용 가능한 상황만 검색하도록 바꾼다.
- [ ] 긴 행동 전체 대신 재사용 가능한 짧은 기술 단위로 나누고 새 과제에서 효과를 본다.

## 9. 최종 회고

- [ ] 새로 배운 기술과 이전 기술의 단순 조합을 각각 한 사례씩 적는다.
- [ ] 기술을 너무 잘게 또는 크게 나눴을 때 생긴 손해와 내 기준을 정리한다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
