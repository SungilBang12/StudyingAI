# Week02 - Perplexity

> [!abstract] 이번 주의 설계 질문
> 검색 결과를 모으는 능력과 근거 있는 답변을 만드는 능력을 따로 조정한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 질문 → 검색어 생성 → 웹 검색 → 원문 선별 → 답변 합성 → 주장별 인용

## 1. 핵심 원리 이해

- [ ] 검색 품질과 생성 품질을 분리하고, 답이 틀렸을 때 어느 단계가 원인인지 설명한다.
- [ ] 최신성·관련성·출처 신뢰성이 서로 다른 기준임을 실제 검색 결과로 확인한다.

## 2. 시스템 아키텍처 관찰

- [ ] 질문이 검색어로 바뀌고 여러 원문이 최종 주장으로 합쳐지는 과정을 추적한다.
- [ ] 검색 API 결과, 자체 합성 파이프라인, 소비자용 제품의 동작을 구분해 기록한다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 자체 구현에서 검색어 수 1/3/5, 결과 수, 날짜 제한, 허용 도메인을 조정 후보로 정한다.
- [ ] 원문 읽기 길이와 인용 검증 기준을 후보로 두고, 사용하는 API가 실제 지원하는 옵션을 확인한다.

## 4. Baseline 구현

- [ ] 공개 웹 질문 10개에 검색 → 상위 원문 읽기 → 인용 포함 답변을 연결한다.
- [ ] 검색 결과와 접근 날짜를 저장해 반복 실험에서 웹 변화가 결과를 섞지 않도록 한다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 저장한 검색 결과에서 답변에 제공하는 원문 수만 2/5/8개로 바꾼다.
- [ ] 모델과 질문을 고정하고 추가 자료가 정확도를 높였는지 중복만 늘렸는지 비교한다.

## 6. 성능 측정 지표

- [ ] 인용 정확도 = 연결된 원문이 지지하는 인용 주장 수 / 인용 주장 수를 계산한다.
- [ ] 중요 주장 중 인용된 비율, 독립 출처 수, 전체 응답 시간, 호출 비용을 기록한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 제목은 관련 있지만 본문은 무관한 페이지와 오래된 자료를 섞는다.
- [ ] 서로 베낀 세 페이지를 독립된 세 근거로 착각하는지, 접근 실패 원문을 인용하는지 확인한다.

## 8. 내 방식으로 재설계

- [ ] ‘많은 링크’보다 ‘주장마다 가장 직접적인 근거’를 우선하는 선별 규칙을 만든다.
- [ ] 사실·해석·미확인을 구분하는 답변 형태를 적용하고 읽는 사람이 검증하는 시간을 비교한다.

## 9. 최종 회고

- [ ] 검색 실패와 합성 실패를 각각 한 사례씩 정리한다.
- [ ] 내가 믿을 만하다고 느끼는 답변의 조건과, 자료를 더 찾아도 멈춰야 할 기준을 적는다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
