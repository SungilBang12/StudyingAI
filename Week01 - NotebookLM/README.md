# Week01 - NotebookLM

> [!abstract] 이번 주의 설계 질문
> 문서에 근거한 답변을 넘어, 자료를 비교하고 생각을 발전시키는 작업 공간을 설계한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

여기서부턴 이전 README
**학습용 흐름:** 문서 → 분할·색인 → 근거 검색 → 답변 생성 → 출처 확인 → 후속 질문

## 1. 핵심 원리 이해

- [ ] RAG에서 모델의 사전 지식과 제공한 문서의 근거가 어떻게 다른지 설명한다.
- [ ] 인용이 붙어 있다는 사실과 인용 문장이 실제 주장을 뒷받침한다는 사실을 구분한다.

## 2. 시스템 아키텍처 관찰

- [ ] 같은 질문의 답변에서 주장·인용·원문을 연결하고, 자료 선택이 사고 흐름에 주는 영향을 관찰한다.
- [ ] 위 흐름은 학습용 개념도임을 기록하고, 비공개 검색·색인 구현을 제품의 실제 내부 구조로 단정하지 않는다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 제품에서는 선택 자료, 질문의 범위, 비교 기준을 조정한다.
- [ ] 자체 RAG에서는 chunk size 200/500/1000 tokens, overlap, top-k를 후보로 적는다. 제품에 해당 설정이 있다고 가정하지 않는다.

## 4. Baseline 구현

- [ ] 공개 문서 또는 공유 가능한 노트 5개와 근거가 명확한 질문 10개를 준비한다.
- [ ] 문서 분할 → 검색 → 근거와 함께 답변하는 작은 RAG를 만들고, 출처 위치와 답변 불가 처리를 남긴다.

## 5. 한 변수씩 바꾸는 실험

- [ ] top-k와 모델을 고정하고 chunk size만 바꿔 같은 질문 10개에 답한다.
- [ ] 품질이 바뀐 답변 2개에서 문맥 단절인지 불필요한 근거 유입인지 원문으로 확인한다.

## 6. 성능 측정 지표

- [ ] 근거 충실도 = 근거로 지지되는 사실 주장 수 / 전체 사실 주장 수를 계산한다.
- [ ] 정답 근거의 Recall@k, 답변 불가 문제의 올바른 보류율, 응답 시간과 토큰 사용량을 기록한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 정답이 없는 질문과 서로 충돌하는 문서를 넣어 추측·충돌 표시·답변 보류를 확인한다.
- [ ] 자체 구현에서 chunk를 매우 작게 하거나 무관한 문서를 늘려 근거가 사라지는 지점을 찾는다.

## 8. 내 방식으로 재설계

- [ ] 내가 원하는 성질을 ‘바로 답하기’ 또는 ‘자료를 비교하며 질문하기’ 중 하나로 정한다.
- [ ] 주장별 근거 카드나 상충 근거 비교 중 하나를 구현하고 기존 답변과 비교한다.

## 9. 최종 회고

- [ ] 자료를 더 넣었는데 이해가 나빠진 사례와 그 원인을 기록한다.
- [ ] 가장 아름다웠던 사고 보조 방식, 유지할 설정, 아직 확인하지 못한 내부 동작을 적는다.
