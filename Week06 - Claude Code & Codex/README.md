# Week06 - Claude Code & Codex

> [!abstract] 이번 주의 설계 질문
> 코드 생성보다 문맥 수집·수정·검증이 연결되는 작업 환경을 이해한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 요청 → 저장소 탐색 → 변경 계획 → 파일 수정 → 테스트·diff 확인 → 수정 또는 완료

## 1. 핵심 원리 이해

- [ ] 모델의 추론과 파일 읽기·편집·실행 도구의 역할을 분리해 설명한다.
- [ ] 테스트 통과와 사용자 요구 충족이 다른 이유를 작은 버그 사례로 확인한다.

## 2. 시스템 아키텍처 관찰

- [ ] 수정할 함수의 호출자와 데이터 흐름을 읽고, 에이전트가 어떤 문맥을 놓치는지 관찰한다.
- [ ] 도구 결과가 다음 행동을 바꾸는 지점과 최종 완료 판단의 근거를 추적한다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 제공할 문맥의 범위, 요청의 구체성, 검증 명령, 허용 작업 범위를 후보로 적는다.
- [ ] 모델·추론 옵션·반복 한도는 현재 도구에서 노출되는지 먼저 확인하고, 미지원 설정을 실험 변수로 삼지 않는다.

## 4. Baseline 구현

- [ ] 복사한 작은 저장소에 재현 가능한 버그 하나와 실패하는 검증 하나를 준비한다.
- [ ] 한 도구로 수정 → 검증 → diff 확인을 수행하고 시작 상태와 실행 기록을 보관한다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 같은 시작 상태에서 ‘증상만 설명’과 ‘증상+재현 절차’로 문맥 조건 하나만 바꾼다.
- [ ] 두 제품을 비교할 때는 별도 실험으로 진행하고, 모델·도구 차이 때문에 원인을 단정할 수 없음을 적는다.

## 6. 성능 측정 지표

- [ ] 재현 문제 해결 여부, 기존 동작 회귀 여부, 불필요한 수정 파일 수를 기록한다.
- [ ] 총 소요 시간, 사람이 개입한 횟수, 사용량이 제공되면 토큰·비용을 함께 기록한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 샌드박스 복사본에서 오래된 README나 불완전한 테스트를 제공해 잘못된 완료 판단을 관찰한다.
- [ ] 같은 함수의 다른 호출 경로가 남아 있는 버그를 넣어 증상만 고치는지 확인한다.

## 8. 내 방식으로 재설계

- [ ] 내가 원하는 작업 기준을 ‘호출자 확인 → 최소 수정 → 실패 재현 검증’처럼 짧게 정의한다.
- [ ] 해당 도구가 지원하는 프로젝트 지침에 적용하고, 같은 유형의 새 버그에서 효과를 확인한다.

## 9. 최종 회고

- [ ] 실제 원인을 고친 수정과 겉으로만 통과한 수정을 비교한다.
- [ ] 사람이 가장 가치 있게 개입한 순간과 앞으로 자동화할 검증을 하나씩 적는다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
