# Week07 - Cursor Agent

> [!abstract] 이번 주의 설계 질문
> 에이전트의 변경을 사람이 빠르고 정확하게 검토할 수 있는 협업 방식을 설계한다.

> [!tip] 진행 방법
> **Build → Measure → Tune → Break → Rebuild.** 먼저 baseline 하나, 변수 하나의 비교 실험, break test 하나를 끝낸 뒤 나머지를 확장한다. 아래 수치와 실습 규모는 학습용 제안이며 제품의 기본값이나 최적값이 아니다.
> 제품 관찰과 직접 만드는 축소 구현을 구분한다. 공개되지 않은 내부 구조는 관찰·가설로 표시하고, 실제 사용한 제품·모델·라이브러리 버전을 기록한다.

**학습용 흐름:** 작업 요청 → IDE 문맥 선택 → 탐색·편집 → 변경 diff → 테스트 → 사람의 검토

## 1. 핵심 원리 이해

- [ ] 코드 제안과 여러 파일에 걸친 작업 실행이 요구하는 검증 차이를 설명한다.
- [ ] 사람이 수락한 변경과 올바른 변경을 같은 지표로 취급하지 않는다.

## 2. 시스템 아키텍처 관찰

- [ ] 현재 파일·명시한 파일·프로젝트 규칙 중 어떤 문맥이 실제 작업에 반영되는지 기록한다.
- [ ] 파일 수정, 실행 결과, diff, 완료 설명 사이에 빠진 증거가 없는지 관찰한다.

## 3. 조정 가능한 변수 (Knobs)

- [ ] 요청 크기, 명시적으로 제공하는 관련 파일, 프로젝트 규칙의 길이를 조정 후보로 정한다.
- [ ] 사용하는 버전에서 제공하는 모드·도구 허용 범위를 확인하고 실험 조건으로 기록한다.

## 4. Baseline 구현

- [ ] 작은 UI 또는 로직 수정 하나를 맡기고 수락 전에 diff를 읽는 절차를 수행한다.
- [ ] 기대 동작과 수정하면 안 되는 동작을 각각 한 문장으로 적고, 재현 가능한 확인 절차를 만든다.

## 5. 한 변수씩 바꾸는 실험

- [ ] 같은 시작 상태에서 관련 파일을 명시하는 조건 하나만 바꾸고 수정 범위를 비교한다.
- [ ] 별도 실험으로 한 번에 맡기는 작업 크기만 늘려 검토 시간이 어떻게 변하는지 본다.

## 6. 성능 측정 지표

- [ ] 요구사항 통과율과 변경당 검토 시간을 기록한다.
- [ ] 검토 중 발견한 오류 수, 수락 후 발견한 회귀 수, 불필요한 변경 줄 수를 구분한다.

## 7. 의도적으로 망가뜨리는 Break Test

- [ ] 비슷한 이름의 파일 두 개와 오래된 주석을 포함한 복사본에서 잘못된 수정 대상을 고르는지 확인한다.
- [ ] 기능은 맞지만 접근성 또는 오류 처리가 깨지는 변경을 검토 절차가 잡아내는지 시험한다.

## 8. 내 방식으로 재설계

- [ ] 내가 쉽게 판단할 수 있도록 요청을 한 동작 단위로 줄이고 검증 결과를 함께 요구한다.
- [ ] 검토용 체크를 ‘요구 충족·범위·회귀’ 세 항목으로 정리한 뒤 다른 작은 수정에 적용한다.

## 9. 최종 회고

- [ ] 변경 내용은 같아도 검토가 쉬워진 조건이 무엇인지 적는다.
- [ ] 에이전트의 설명을 믿었던 순간과 실제 diff·실행 결과로 판단한 순간을 비교한다.

## 실험 기록

> [!note] 비교 원칙
> 입력·평가 사례·모델·예산을 고정하고 변수 하나만 바꾼다. 확률적인 결과는 가능하면 조건별 3회 이상 반복해 평균 또는 중앙값과 범위를 함께 적는다. 개선안 선택에 쓴 사례와 최종 확인 사례를 구분한다. Break test는 복사본·합성 자료·모의 환경에서 수행한다.
